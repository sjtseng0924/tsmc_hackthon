tNote 系統事故結案報告 (Post-Mortem Report)
文件編號: INC-20230815-04
報告日期: 2023-08-16
事件標題: 因排程腳本錯誤清除環境變數導致的檔案上傳失敗事件

1. 基本資訊
Issue 發生時間: 2023-07-15 00:00 UTC
Issue 解決時間: 2023-07-15 02:30 UTC (服務功能恢復)
事件等級: P1 (主要功能障礙)
2. 報案問題
自 00:00 UTC 起，所有使用者回報無法上傳任何檔案至 tNote，系統返回錯誤訊息「Upload Failed: Permission Denied」。
除了檔案上傳外，系統其他功能（如筆記編輯、查看）均正常。
3. 影響範圍
服務影響:
檔案上傳功能完全中斷。
使用者影響:
全球所有使用者。
資料影響:
無資料遺失。
4. Issue 發生細節描述
根本原因 (Root Cause):
每日 00:00 UTC 執行的排程腳本 cache_cleanup_v2.sh 中，包含了一段錯誤的「安全清理」程式碼。該程式碼執行了 unset 指令，清除了運行後端服務的伺服器環境中的 AWS 臨時憑證變數 (AWS_SESSION_TOKEN, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY)。

事件細節:

環境變數被清除: 在 cache_cleanup_v2.sh 腳本執行結束前，其 unset 指令生效，導致與該腳本共享相同執行環境的 tNote 後端服務進程遺失了用於向 AWS S3 進行身份驗證的憑證。
上傳請求失敗: 當後端服務收到新的檔案上傳請求時，它嘗試使用空的憑證向 S3 請求上傳權限，被 AWS IAM 服務理所當然地拒絕，從而向前端返回了「Permission Denied」錯誤。
問題的隱蔽性: 由於 IAM 角色、S3 儲存桶策略等靜態配置均未改變，初步調查方向一度陷入僵局。直到工程師將問題發生時間與排程工作關聯起來，並審查了 cache_cleanup_v2.sh 的腳本內容，才最終定位到問題。
事件時間軸:

00:00 UTC: cache_cleanup_v2.sh 腳本開始執行。
00:02 UTC: 腳本執行完畢，其中的 unset 指令生效。
00:03 UTC: 系統監控平台開始記錄到檔案上傳 API 的 403 Forbidden / Permission Denied 錯誤率飆升至 100%。
01:00 UTC: War room 成立。團隊確認了所有雲端權限配置均正確無誤。
01:45 UTC: 工程師注意到錯誤率從 00:03 UTC 開始飆升，將懷疑重點放在了 00:00 UTC 的排程工作上。
02:00 UTC: 團隊審查了 cache_cleanup_v2.sh 腳本，發現了結尾處的 unset 指令，確認為根本原因。
5. 解決方案 (Immediate Fix)
修復並部署腳本:
從 cache_cleanup_v2.sh 腳本中註解掉所有 unset 相關的行。
立即將修復後的腳本部署到生產環境。
重啟服務:
對所有後端應用程式伺服器進行滾動重啟，以強制服務重新從系統配置中載入正確的 AWS 憑證。
驗證恢復:
QA 團隊驗證檔案上傳功能已恢復正常。
6. 之後如何避免 (Prevention Measures)
行動項目 1: 隔離腳本執行環境

內容: 確保所有高風險的排程工作都在一個獨立、隔離的容器或子 Shell 環境中執行。這樣，即使腳本修改了環境變數，也不會影響到主應用程式服務的運行環境。
負責人: DevOps Team
截止日期: 2023-08-01
行動項目 2: 強化程式碼審查檢查清單

內容: 在 Code Review 的檢查清單中明確增加一項：「檢查腳本是否包含任何可能影響共享環境的命令（如 export, unset, source）」。
負責人: All Engineering Leads
截止日期: 2023-08-14
行動項目 3: 增加應用程式健康檢查維度

內容: 在後端服務的 /health 健康檢查端點中，增加一項檢查，用於確認必要的環境變數（如 AWS_REGION）是否存在。如果不存在，則將服務標記為不健康，以便負載均衡器能及時將其移除。
負責人: Backend Team
截止日期: 2023-08-15
[已關閉] 行動項目 4: 全面審查 cache_cleanup_v2.sh

內容: 對 cache_cleanup_v2.sh 進行全面審查，確保沒有其他潛在問題。
結論: 團隊審查了腳本中的防火牆操作部分，認為其 trap 機制是合理的，用於確保臨時打開的端口被關閉，未發現其他問題。
