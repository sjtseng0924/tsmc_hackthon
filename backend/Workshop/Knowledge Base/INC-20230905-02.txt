tNote 系統事故結案報告 (Post-Mortem Report)

文件編號: INC-20230905-02
報告日期: 2023-09-06
事件標題: 因資料庫連線池耗盡導致的使用者登入 500 錯誤事件


1. 基本資訊

Issue 發生時間: 2023-09-05 14:00 UTC

Issue 解決時間: 2023-09-05 15:30 UTC (服務功能恢復)

事件等級: P1 (主要功能障礙)


2. 報案問題

大量使用者回報，在登入 tNote 系統時，頁面顯示「500 Internal Server Error」。

已登入的使用者回報，部分操作（如建立新筆記本）反應極度緩慢或最終失敗。


3. 影響範圍

服務影響:

使用者登入功能完全不可用。

部分需要新資料庫連線的內部功能失敗。

使用者影響:

所有嘗試登入或啟動新會話 (Session) 的使用者。

資料影響:

無資料遺失。 此為服務可用性問題。


4. Issue 發生細節描述

根本原因 (Root Cause):
後端應用程式的資料庫連線池 (Database Connection Pool) 完全耗盡。

問題源於當天 13:45 UTC 部署的一個新功能：「活躍使用者儀表板小工具 (Active Users Dashboard Widget)」。該小工具的後端程式碼存在嚴重缺陷：

連線洩漏 (Connection Leak): 該功能的程式碼在一個迴圈 (loop) 中為每一個需要顯示的活躍使用者都建立了一個新的資料庫連線，而不是從連線池中請求並在使用後歸還。

未關閉連線: 更嚴重的是，這些在迴圈中建立的連線在使用完畢後並未被正確關閉。它們變成了閒置但佔用名額的「殭屍連線」，迅速佔滿了整個連線池。

當連線池滿載後，任何需要資料庫連線的新請求（例如，驗證使用者密碼的登入請求）都無法從池中獲取可用連線。在等待超時後，應用程式服務因無法完成任務而只能向前台返回「500 Internal Server Error」。

事件時間軸:

13:45 UTC: 包含「活躍使用者儀表板」新功能的 v2.5.1 版本部署上線。

14:00 UTC: 隨著越來越多的使用者（特別是管理員）登入並看到新的儀表板，資料庫連線池被迅速耗盡。系統監控開始記錄到登入 API 的 500 錯誤率急劇上升。

14:10 UTC: War room 成立。初步檢查發現認證服務本身運行正常，資料庫也處於健康狀態，未觸發高 CPU 或記憶體警報。

14:30 UTC: 工程師檢查應用程式層面的監控指標，發現「資料庫連線池使用率」在 14:00 左右達到 100% 並一直維持在該水平。

14:45 UTC: 團隊將連線池耗盡與 v2.5.1 的部署時間點關聯起來，開始審查新功能的程式碼。

15:10 UTC: 在審查「活躍使用者儀表板」的後端程式碼時，發現了嚴重的連線洩漏問題，確認為根本原因。


5. 解決方案 (Immediate Fix)

功能降級: 透過功能開關 (Feature Flag) 遠程禁用「活躍使用者儀表板」功能，阻止有問題的程式碼被繼續執行。

服務重啟: 對所有後端應用程式伺服器進行滾動重啟 (Rolling Restart)，以強制關閉所有已洩漏的資料庫連線，並重置連線池。

驗證恢復: 重啟完成後，由 QA 團隊驗證登入功能已恢復正常。


6. 之後如何避免 (Prevention Measures)

行動項目 1: 引入靜態程式碼分析工具

內容: 在 CI/CD 流程中整合一個靜態程式碼分析工具（如 SonarQube），並設定規則來檢測在迴圈內建立資料庫連線或未關閉資源的程式碼模式。若檢測到此類問題，則阻斷建置流程。

負責人: DevOps Team

截止日期: 2023-10-01

行動項目 2: 建立資料庫連線池監控警報

內容: 在監控系統中設定一個新的高優先級警報：當「資料庫連線池使用率連續 5 分鐘超過 90%」時，直接向 on-call 工程師發送 P1 警報。

負責人: SRE Team

截止日期: 2023-09-15

行動項目 3: 強化效能審查流程

內容: 對於所有涉及新資料庫查詢模式或迴圈處理資料的功能，強制要求進行效能專項的程式碼審查。審查者需特別關注資源（連線、記憶體）的申請與釋放是否正確。

負責人: All Engineering Leads

截止日期: 2023-09-20

行動項目 4: 統一資料存取層

內容: 推動開發團隊使用統一的資料存取層 (Data Access Layer) 或 ORM (Object-Relational Mapping) 框架來處理資料庫互動，避免開發人員直接操作底層資料庫連線，從架構上減少此類錯誤的發生機率。

負責人: Architecture Team

截止日期: 2023-11-01
